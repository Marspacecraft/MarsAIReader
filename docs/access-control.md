# 代码访问权限 v0.2（三条判定已实现）

**这份文档回答什么问题**：谁（哪一类代码）可以读哪个目录、可以写哪个目录；这个约定凭什么能被机器判定，而不是靠自觉。

数据的唯一来源是仓库根目录的 `policy.txt`。本文只写语义、理由和失败模式，**不复制那张表**——表在 `policy.txt` 里，抄一份到这里就会漂移（见 docs/README.md 纪律 8）。

---

## 1. 模型

两个维度：**角色**（谁）与**路径**（哪里）。

| tag | 角色 | 是什么 |
|---|---|---|
| 1 | `sysapp` | 系统 App：0 号管理器 + 各服务 App（**产品仓库**） |
| 2 | `aiapp` | AI 写的 App（**产品仓库**） |
| 3 | `framework` | 框架层 |
| 4 | `platform-fake` | 虚拟平台（PC 上跑门禁） |
| 5 | `platform-metalio-eink-4-plus` | 首块真实板 |
| 6 | `platform-other` | 其他移植平台 |

> 本仓库**不含 `apps/`**（用户 m01960/m01994）。下表与示例里的 `apps/...` 是**产品仓库**
> 的路径：策略表在两个仓库共用，本仓库自身只用到 tag 3/4/5/6 的行。

每个角色声明两样东西：

- **身份**：`writes` 前缀，说明"这个角色的代码住在哪个目录"。一个文件的角色 = 匹配它的最长 `writes` 前缀。**没有匹配 = 没人能写，只有人能写。**
- **读权限**：由 `[read]` 表按路径前缀授予。

写入权限是白名单：**没写进去的路径，谁都不能写**。因此不需要一条条写"禁止"——AI 不能写 `framework/`，不是因为它被禁止，而是因为没有任何角色的 `writes` 覆盖那里。

只有人能写的目录（刻意留白）：`common/`、`api/`、`platform/port/`、`platform/drivers/`、`platform/boards/`、`skills/`、`docs/`、`tests/`，以及全部构建文件与 CI。

## 2. 四条语义（缺一条就有歧义）

### 2.1 `r` 的含义：允许 include / 链接，不是禁止阅读源码

同一份 checkout、同一个文件系统，**没有任何工具能阻止一个 agent 去读一个文件**。所以：

- `r` = 这个角色的代码可以 `#include` 该路径的头、可以链接该路径导出的符号。
- `r` ≠ 保密。想要真正的保密只能物理隔离（子模块、独立仓库、不同权限的 CI runner）。

把 `r` 当成保密边界，会在第一次 code review 时发现它不成立，然后整套约定被当成"形式主义"丢掉。

### 2.2 最长前缀优先

`apps/` 与 `apps/system/` 会同时命中一个路径。规则是**取最长的匹配**：

- 标记 2 读 `apps/app_manifest.h` → 命中 `apps/` → 允许
- 标记 2 读 `apps/system/manager/manager.h` → 命中 `apps/system/` → 拒绝

没有这条，`apps/` 上的 `r` 会把 `apps/system/` 一起放开。

### 2.3 未列出的路径 = 无人可读写

`policy.txt` 里没出现的路径，默认拒绝。这条必须显式写进规格：默认允许的话，新增一个目录就等于默认对所有角色开放，而这个"开放"不会出现在任何 diff 里。

### 2.4 一个文件只属于一个角色

`writes` 前缀之间不得重叠到同一个文件。重叠意味着"这个文件的角色"不唯一，判定结果取决于遍历顺序——那种 bug 表现为"有时拦、有时不拦"，最难查。

## 3. 权限表

表在 `policy.txt`。要点：

- `api/` 对 1/2/3 可读；`api/sys/` 只对 1/3 可读——**AI 拿不到机制面**（`app_run_exit` / `app_cancelled`），伪阻塞才是"框架一处保证"而不是"每个作者各自记得做"。
- `framework/` 对 1/3 可读，只有 3 可写。系统 App 必须能读控制面，否则管理器启动不了别人。
- `platform/` 对 3/4/5/6 可读，但被更具体的前缀收紧成"每个平台只能读自己的实现目录"。
- `apps/app_manifest.c` 归标记 2（AI）写：加 App 必须往注册表加一行，这是唯一一处 AI 要碰的共享文件。

## 4. 判定机制

三处判定，全部是集合包含，无运行时开销。

### 4.1 依赖：用编译器的真实解析结果，不自己解析 include

对每个源文件跑一次预处理器，取它实际展开到的**每一个头的绝对路径**：

```
clang -std=c11 -M -I<该角色允许的 include 路径> -c apps/demo/x/app.c
```

输出里的每个依赖路径都必须落在该角色可读的路径里（按 §2.2 判）。

**为什么不用正则扫 `#include` 行**：正则只能看字面量，而 C 的 include 解析是编译器行为——`../` 相对路径、`-I` 搜索顺序、`#include_next`、`__has_include`，每一条都能绕过字面匹配。用 `-M` 拿到的是编译器自己的答案，无处可绕。

### 4.2 符号：看"这个符号有没有出现在你实际 include 过的头里"

编译完成后，取两样东西：

```
clang -std=c11 -I<允许的路径> -c apps/demo/x/app.c -o app.o
llvm-nm --undefined-only -g app.o     # 这个单元用到了、但没在自己这里定义的符号
```

判据不是"符号定义在哪个目录"，而是：**该未定义符号必须出现在这个编译单元实际
include 过的某个头文件里**（4.1 那一步已经拿到了真实依赖列表，在这些头的文本里
查标识符即可）。

三条推论：

- `api/` 里声明、`framework/` 里实现的函数（`app_delay`、`app_log`）**顺利通过**——
  声明就在 App include 的头里。按"定义位置"判会把所有正常调用当违规，那样门禁没法用。
- `extern void app_run_exit(void);` **被拦住**——这个标识符不出现在任何被 include 的头里。
- 仓库里找不到定义的符号（`memcpy`、`snprintf`）是外部依赖，不判。

**为什么必须有这一条**：不 include 任何头，直接

```c
extern void app_run_exit(void);
```

就能调用任意符号。C 没有访问控制，include 白名单对它完全无效。而任何形式的越权最终都要落到符号表上——`extern`、函数指针、宏拼接、改名 include 都一样。这一条把"权限"从文本约定变成链接事实。

### 4.3 写入：路径前缀

`git diff --name-only` 的每个路径，所属角色必须对该路径有 `w`。CI 与本地同一条规则。

配套一条针对注册表的细则：**标记 2 对 `apps/app_manifest.c` 只能追加**（不得删除或修改既有行）。否则 AI 可以把自己的 App 写成 `APP_FLAG_SYSTEM`，或把管理器从清单里删掉。这条判定的实现是"diff 只增 + 新增行必须引用 `apps/demo/` 下的对象"。

**身份必须显式声明**：写入判定要拿"我是谁"去查表，脚本不会猜。
`--as <tag|human>`。不声明时脚本打印

```
SKIP 未声明身份（--as <tag|human>）。
这不是通过：CI 里必须声明身份，否则等于没判。
```

并且**不计为违规**（否则每次本地跑全量门禁都会被自己的身份缺失卡住）。
依赖与符号判定与身份无关，任何时候都跑。

## 5. 为什么值得做

- **AI 是主要开发者**：靠文档说"不要碰 framework"是一次性约定；下一次会话它就不记得了。写成策略表 + 三条判定，才是每次都会被检查的。
- **失败是静默的**：AI 绕过框架直接调器件，代码能编译、能跑、甚至看起来正常，直到换板时才发现这一层根本没起作用。这类问题在运行时不报错，只能在构建期拦。
- **成本低**：整张表是数据，判定是集合查找；三条检查跑完是秒级。

## 6. 常见任务要改哪些文件

| 任务 | 改 | 不改 |
|---|---|---|
| AI 加一个 App | `apps/demo/<app>/` + `apps/app_manifest.c` 追加一行 | 其它一切 |
| 加一个系统 App | `apps/system/` | `api/`（除非要暴露新能力） |
| 新增一个能力（如 `disp`） | `api/include/disp.h` + `framework/src/` 或服务 App + `policy.txt` 里加一条 `read` 行 | 各平台目录 |
| 移植一块新板 | `platform/<board>/` + `policy.txt` 加一条 `role` 行和一条 `read` 行 | `framework/`、`api/` |

最后一行是需要留意的代价：**加平台要动 `policy.txt`**。这是刻意的——新平台意味着新的写入区域，这应该出现在 diff 里。

### 7.1 为什么改成目录（推翻决定 16）

16 的理由是"目录可以被挪文件绕过"。这条理由在**写入**上成立，但写入本来就由 §4.3 按路径前缀判定——路径前缀天然知道 `apps/system/`。也就是说：目录方案并不是"没有清单就没人管"，而是**把清单换成了路径前缀**，而路径前缀恰好是写入判定本来就要用的东西。

代价与收益：

- 收益：少一份需要与目录同步的数据；`apps/` 的结构一眼能看出谁是谁。
- 代价：必须显式禁止标记 2 写 `apps/system/**`（白名单天然做到：标记 2 的 `writes` 不含该前缀）。

## 9. 为什么数据格式是行格式而不是 TOML/JSON

- **TOML**：本机 python 是 `3.11.0a3`，没有 `tomllib`（它要 3.11 正式版），而 `pip install tomli` 在这个环境装不上（网络受限）。用一个本地无法解析的格式描述策略，等于让策略表无法自校验。
- **JSON**：`json` 是标准库，但放不下注释——而这个文件的注释承载着"为什么"，删掉就会被人重新讨论一遍。
- **行格式**：零依赖、`diff` 友好、与仓库里已有的 `tools/purity_rules.txt` 同一种写法。代价是不能嵌套——但权限表本来就只是两张平面表。
