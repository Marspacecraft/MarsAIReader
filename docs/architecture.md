# MarsAIReader 架构设计（v0.4）

> **定位：本项目是框架，不针对任何具体硬件。**
>
> 本仓库交付：**框架层完整实现** + **应用层必要实现** + **平台层接口要求** + **skill 与门禁**。
> 平台层（引脚、总线、上电时序、面板传输、器件驱动）由**不同硬件平台的外部实现**提供，契约见 [platform-port.md](platform-port.md)。
>
> 状态：仅设计，未实现。屏幕因特殊性**单独讨论**（§9）。

> **语言边界**：本仓库内的 `common/` `api/` `lib/` `framework/` 一律是**标准 C11**，与任何目标 SDK、芯片、图形库无关（产品仓库的 `apps/` 同样受约束）。编译器差异只收敛在 `common/include/cm_port.h`；这条规则由 `tools/check_purity.py` 强制。平台差异由平台包在 `platform/` 里吸收，不向上渗透。

## 0. 分层与解耦

```
common/              人人可用的基础设施（类型、原子、链表、错误码、TLS）
api/                 应用层契约面：公共头 + 能力目录（无实现）
framework/           框架层：不能运行的代码（无 task / 无 timer / 无硬件句柄）
platform/port/       平台层接口要求：plat_ops_t + NULL 表示不支持
skills/              给 AI 的工作流与硬约束
tests/               host 单测（含 host-fake 平台）

apps/                ← 不在本仓库，由产品仓库提供
  系统 App          引导、生命周期、监控、配额、能力汇总；服务宿主（display/input/audio/net）
  业务 App          AI 写：只调 api/
```

**`apps/` 为什么不在本仓库**：本仓库只做框架 + 应用层公共逻辑（用户 m01960/m01994）。
App 实现、0 号策略、各服务 App 都属产品侧；框架只提供机制与清单合并
（`fw_init(manifests, count)`），不认领任何具体 App。

### 0.1 解耦规则

| 规则 | 说明 |
|---|---|
| 只能调**相邻下一层** | `apps → framework → platform`；app 不得直接调 `plat_*` |
| 不允许跨层 | app 不得 include `platform/`；platform 不得 include `apps/` 与 `api/` |
| 同层可调 | app 调 app 允许（reader 调 display 的接口），这是"服务"的形态 |
| framework 不持有运行权 | 无 task、无 timer、无队列实例；机制绑定在宿主 App 上执行 |
| framework 不 push 给 app | 只提供 wait/peek，App 自己 pend —— 这就是"框架不能调用应用" |
| **platform 只实现 port** | 平台包不认识任何 App，只知道 `plat_ops_t` 与能力位 |

### 0.2 唯一例外：事件从下往上走

若严格要求"只能向下调用"，平台的中断 / DMA 完成回调将**无法产生事件**。因此开一条白名单：

```c
/* platform → framework 允许调用的全部函数，仅这两个 */
void fw_event_post(evt_topic_t topic, const void *payload, size_t n);   /* 任务上下文 */
void fw_event_post_isr(evt_topic_t topic, const void *payload);         /* ISR 上下文 */
```

- 只能调这两个；不得调 framework 其它函数，**不得调任何 app**。
- framework 仍然不调 app：事件只是入队，App 自己 `app_wait_msg()` 取。
- 这条白名单可用 include / 符号图静态检查。

## 1. App 的定义

App = **一个模块 + 一个主任务 + 一份 manifest**。它不是进程，没有地址空间隔离；价值是**可被调度、可被停止、可被计量**。

```c
typedef struct app_desc {
    app_id_t    id;                            /* 1..254，全固件唯一（0 保留） */
    const char *name;                          /* 给人看的名字：日志、UI */
    cm_err_t (*init)(app_ctx_t *ctx);          /* 建资源 */
    void     (*exit)(app_ctx_t *ctx);          /* 所有结束路径都调用恰好一次 */
    void     (*task)(app_ctx_t *ctx);          /* 主任务体，必须可协作退出 */
    uint32_t    flags;                         /* APP_FLAG_SYSTEM */
} app_desc_t;
```

> 权威定义是 `api/include/app.h`；完整契约（伪阻塞、退出顺序、已知缺口）见
> [app-model.md](app-model.md)。本节只保留架构层面的形态。

### 1.1 主任务的强制形态

```c
for (;;) {
    do_work();
    app_delay(100);   /* 伪阻塞：被取消时不返回这里，直接走退出路径 */
}
```

没有 `app_wait_msg(...) == OK` 这种写法。**App 不检查返回值、不写状态机、不轮询取消位**——
一旦写了，就等于把"停得下来"这件事从框架的保证降级成作者的自律。

### 1.2 停止协议（为什么不能强杀）

`vTaskDelete` 一个卡在 `while(1)` 里、还**持着互斥锁**的任务 → 锁永远不还 → 整机从"某 App 卡住"恶化为"全系统死锁"。

1. 0 号置状态 `STOPPING` 并置取消位（**不投递"停止消息"**，App 不需要处理它）；
2. 任务在下一个伪阻塞点发现取消位 → 清零取消位（= 在 exit 期间禁用取消）→ 调 `exit()` → 置终态 → 结束任务；
3. **超时未退** → 当前只观测并报告（0 号不打日志刷屏，只在状态变化时打一行）；自动重启策略未实现；
4. 极端情况只能重启整机。

> **能力上限要写进 skill**：这是"有界退化"，不是沙箱，AI 不能假设有内存隔离。
> 另外"框架回收托管资源"也还没实现（`res_track`），当前 App 必须自己在 `exit()` 里关掉一切。

### 1.3 状态机

```
EMPTY ──start──> INIT ──init成功──> RUNNING ──request_stop──> STOPPING ──> STOPPED
                   │                    │
               init失败             task 正常返回（自愿退出）
                   └──────> FAILED      └──────────────────────────────> STOPPED

STOPPED ──start──> INIT        （可重启：取消位在收尾时已清零）
```

只有 6 个状态，**没有"暂停"**——单 MCU 上暂停等于"占着资源不干活"。

### 1.4 manifest（部分字段尚未落地）

```yaml
# apps/reader/app.yaml
app:
  id: 3                      # 数字，1..254，全固件唯一（与 app_id_t 一致）
  name: 阅读器                # 人读，日志与 UI 用
  flags: none                # none | system
  stack_bytes: 6144          # 设计：内部 RAM，不能放 PSRAM（当前统一 4096，未按 App 配置）
  psram_bytes: 262144        # 设计：启动前预检，超预算拒绝启动（未实现）
  requires: [display, storage, input]   # 设计：启动依赖，拓扑排序用（未实现）
  services: []               # 设计：对外提供的能力（服务注册表已定，见 §3.6）
```

> 写明"未实现"不是免责，是防止 AI 按设计写代码而在运行时发现字段被忽略。
> 当前真正生效的只有 `id` / `name` / `flags`；其余三项属里程碑 M2。

`requires` 的用意是让 manager 按拓扑序启动、逆序停止；**这条能力还没实现**，现在 0 号只按 manifest 顺序启动。

## 2. 0 号 App（manager）—— 属产品仓库

> 本节描述的是**架构角色**，不是本仓库的代码。本仓库不提供 0 号实现（见 §0）。
> 框架只做两件事：拉起 `APP_FLAG_SYSTEM` 的 App、提供 `fw_app_*` 控制面。
> 下表里标"未实现"的能力，是框架也还没有支撑（如 `requires` 依赖图）。

| 职责 | 说明 |
|---|---|
| 引导 | 唯一在框架初始化前存在的执行体（由 `app_main()` 创建），第一件事是 `fw_init()` |
| 启动编排 | 读所有清单，决定启动谁、什么顺序；**依赖图/拓扑排序尚未实现**，当前只能按清单顺序 |
| 配额预检 | 累计 `stack_bytes` / `psram_bytes`，超预算在启动前拒绝；**字段尚未实现** |
| 能力汇总 | 读能力位，生成运行时能力表，供 App 查询"本机有没有麦克风"；**caps 未实现** |
| 监控 | 心跳 / 提交超时 / 队列积压；异常先标记 `FAILED`，不直接杀 |
| 停止 | 协作式（§1.2），逆拓扑序 |
| 故障隔离 | `FAILED` 的 App 不再收到投递，依赖它的 App 收到明确错误码 |

**manager 本身只是一个 App**，特殊在"它是唯一能启动别人的人"，而非权限。框架层因此仍然没有运行权。

## 3. 接口契约

### 3.1 三条铁律

**铁律一：框架提供的一切阻塞都是伪阻塞，退出由框架负责。**

App 看到的是普通阻塞函数，看不到"停止"这件事：

```c
int  stor_read(int fd, void *buf, size_t n);   /* 会阻塞 */
void app_delay(uint32_t ms);                   /* 也会阻塞 */
```

框架在其内部实现伪阻塞：

```c
int stor_read(int fd, void *buf, size_t n) {
    int r = plat_storage_read(fd, buf, n);   /* 内部按块等待，每块查取消位 */
    release_internal(fd);                    /* ① 先让自身资源回到一致状态 */
    if (app_cancelled()) app_run_exit();     /* ② 再检查退出码，不返回 */
    return r;                                 /* ③ 未取消才正常返回 */
}
```

> 上面代码里的 `app_cancelled()` / `app_run_exit()` 属于**机制面**（`api/include/sys/app_sys.h`），
> AI 写的 App 看不到它们——它们只出现在框架自己的阻塞点实现里。App 面（`api/app.h`）
> 只暴露 `app_delay()` 这个"会响应停止的延时"，连"取消"这个词都不出现。

**App 不检查返回值、不写状态机、不轮询。** 它写直线代码。这是对 AI 最友好的形态：取消语义完全藏在框架里，AI 不需要为"随时可能被停"设计任何结构。

取消位放在**任务上下文**里：manager 置位，任务在退出时自己清零。App 侧不提供读取它的 API——需要保存状态就写 `on_exit`。

与原表述的差别：原来禁止"阻塞超过 1ms"，现在禁止**不可打断的阻塞**。危险的不是等待，是等不回来。

**铁律二：应用层接口一律「提交即返回、最终一致」。**

```c
disp_err_t disp_commit(const page_t *page);   /* 立即返回，同 key 覆盖 */
```

提交 10 次只刷最后 1 次，是**实现层的职责**，不是 AI 的修养。推论：**AI 没有"刷新"这个动作可用**，从结构上做不到刷坏屏。

需要结果时可以等完成事件——同样是伪阻塞，可被停止打断。

**铁律三：阻塞点只能落在事务边界上。**

框架的阻塞点不得出现在器件时序中间——屏幕的半帧、SD 卡的半个扇区、一段 I2C 复合事务。这些必须在一次不可打断的段内做完，再回到可取消的边界。

#### 3.1.1 退出路径

```
阻塞点发现取消位
  → 标记"正在退出"（此后禁用取消）
  → 框架回收本 App 的全部托管资源
  → 调 App 的 on_exit(ctx)（可选：存阅读进度、落盘草稿）
  → 清取消位
  → 结束任务，不返回调用者
```

**因此资源必须登记在 ctx 上，不能只放在栈上。** 退出可以从任意一个阻塞点发起，那时看不到上层栈帧的局部变量：

```c
/* 对：获取与登记是一次原子动作 */
res_track(&ctx->book_fd, stor_open(path, O_RDONLY));

/* 错：open 返回与赋值之间若被取消，fd 永久泄漏 */
ctx->book_fd = stor_open(path, O_RDONLY);
```

推论：**框架的资源获取接口直接写 ctx 槽位**，App 不持有裸句柄。回收由框架代劳，`on_exit` 只剩业务清理。

#### 3.1.2 四条硬约束

| # | 约束 | 不满足的后果 |
|---|---|---|
| 1 | 每个阻塞点必须可取消 | 停止延迟无上限 |
| 2 | 单段不可打断的等待 < 200ms | 停止延迟 = 当前段长度，超过用户可感知 |
| 3 | 退出处理期间禁用取消 | 清理中被再次取消 → 永不结束 |
| 4 | 只有 App 任务有取消位；平台任务 / 框架初始化 / ISR 不可取消 | 在不可取消的上下文里长阻塞 = 卡死整机 |

第 2 条是唯一能自动检查的：**停止延迟 = 当前阻塞段长度**。这是结果指标，不是手段指标，所以能进门禁。

#### 3.1.3 取消位的生命周期

manager 置位 → 阻塞点发现并生效 → 任务退出时清零 → manager 确认 `STOPPED` 后才允许重启。

**顺序不能反**：若重启前不清零，新任务在第一次阻塞就立刻被杀，表现为"App 起不来"。清零只有任务自己知道确切时刻——这就是"task 自己清理"的必要性。

#### 3.1.4 停止的是 App，不是它已提交的操作

`disp_commit()` 之后操作归 display App 所有；调用者被停止，屏幕继续刷完。否则中断落在刷屏中间是硬件风险。撤销只能用 `disp_cancel(token)`，且只在安全点生效。

#### 3.1.5 死循环不算阻塞

`while (1) { work(); }` 里若没有任何伪阻塞调用，取消位永远不会被看到。两道防线：门禁静态检查（任务体内必须至少有一个伪阻塞调用，`app_delay` 也算）+ 0 号心跳看门狗兜底。

### 3.2 接口分类

| 类型 | 形态 | 阻塞 | 例子 |
|---|---|---|---|
| **提交型**（有状态、长时序） | 投递给 owner，立即返回 + 完成事件 | 否（可自愿等完成事件） | `disp_commit`、`audio_play` |
| **同步型**（无状态、短） | 直接函数调用，内部自带锁 | 伪阻塞，可被停止打断 | `stor_read`、`rtc_now` |
| **延时型** | `app_delay(ms)` | 伪阻塞，按时长分块 | 轮询、动画节拍 |
| **共享流型**（唯一实例） | 无参数 obtain/release + 引用计数 | 否 | `mic_obtain` |

### 3.3 共享资源：不暴露参数

硬件只有一个采样率、一个格式。**接口里就不应该有参数**——没有参数，就不存在"参数不同无法共享"。

```c
mic_h   mic_obtain(void);        /* 无参数；格式由平台定死 */
void    mic_release(mic_h h);
size_t  mic_read(mic_h h, void *buf, size_t n);
```

不提供 `mic_init()`：**没有初始化接口，就没有"谁来初始化、初始化成什么"的协商**。需要别的格式的 App 自己重采样，接口不为此让步。

### 3.4 锁：归请求者，只用于短临界区

| 临界区长度 | 谁持锁 | 形态 |
|---|---|---|
| < 1ms | **请求者** | `res_lock(); op(); res_unlock();` |
| 1~100ms | **请求者** | try-lock + 超时，失败立即返回错误码 |
| **> 100ms** | **不允许用锁** | 提交给 owner，立即返回 + 完成事件 |

判据：**别人能不能容忍等这么久**。等 3 秒刷屏不是锁能解决的，是调度问题，因此它根本不该以"锁"的形态暴露。

### 3.5 不设优先级分带

时间片 1ms 远小于音频 DMA 缓冲（32ms）与触摸采样周期（10ms），同优先级不会造成可感知抖动。

- 所有 App task 用同一个常量优先级，**低于所有 ESP-IDF 系统任务**；
- **不提供**设置优先级的接口 —— 不是靠禁令，是靠没有入口；
- 真正危险的是**关中断**和**忙等不 yield**，那是 §7 的独立规则。

### 3.6 服务的落点：注册表

`api/` 里的功能分两类，实现位置不同，但**对调用方完全一样**：

| 类别 | 例子 | 实现在哪 |
|---|---|---|
| 机制型 | `stor_open`、`res_acquire`、`app_delay` | 框架层 |
| 服务型 | `disp_commit`、`audio_play` | 服务 App + 注册表 |

服务型 API 的实现体在 App 里，但**函数符号属于框架**：框架的转发层持有函数指针，做三件事后转给服务：

1. 未注册 → `NOT_SUPPORTED`（这块板没有这个能力）
2. 已注册但服务 `FAILED` → `UNAVAILABLE`（崩了，可重试）
3. 调用返回前检查取消位 → 已取消则走退出路径

**1 和 2 必须分开**：把"没有这个能力"和"有但暂时坏了"混成一个错误码，UI 就无法区分"隐藏入口"和"提示重试"。

这样做的原因只有一条：**伪阻塞的保证必须落在一处**。若让每个服务自己导出符号，"每个阻塞点都可取消"就从保证退化成"每个作者各自记得做"。

两个次生结论：

- 两个 App 之间不需要互相 include，也不需要知道对方存在；
- 0 号通过注册表就知道"谁提供了什么、现在什么状态"，不必认识任何 App。

## 4. 冲突模型（三层）

硬件唯一性造成的冲突分三层，裁决者与可见性不同：

| 层 | 冲突对象 | 裁决者 | 对应用层可见 |
|---|---|---|---|
| **逻辑层** | 谁在用"喇叭/麦克风/屏幕"这个**功能** | manager + 应用层锁 | **可见** |
| **器件层** | 同一器件的**一整段时序**不能被切开 | 驱动内部会话锁 | 不可见 |
| **总线层** | 同一物理总线 / DMA / 引脚上的**单次事务**不能交错 | 平台层，读自己的板级描述 | 不可见 |

**应用层的锁不映射到总线锁。** 应用层只知道"我要显示这一页"，不知道底下有没有和 flash 抢 SPI。若让应用层管总线锁，换一块板（总线拓扑不同）就要改所有 App。

总线仲裁是**平台包的内部实现**，两级锁都不能省：器件会话锁保护一整段时序，总线锁保护单次事务。

## 5. 资源接口

```c
res_handle res_acquire(res_kind kind, size_t bytes, res_lifetime life);
void       res_release(res_handle h);
```

覆盖：PSRAM、内部 RAM、task 栈、文件句柄、总线使用权。

**只做记账与限额，不重造分配器**：底层仍是 `heap_caps_malloc(MALLOC_CAP_SPIRAM)`。自己实现 buddy/slab 会带来碎片率、PSRAM 访问延迟和一套没人维护的分配器。配额、冲突、回收因此只有一个落点。

## 6. 框架不规定任务数量

"每个硬件一个 task"是**平台实现的事**。框架只规定两件：

1. **task 只能由框架创建**：`app_task_create()` 内部使用固定优先级常量，App 接触不到 FreeRTOS 优先级；
2. **主任务必须事件驱动、有界等待、可协作退出**（§1.1）。

给平台实现者的判据（详见 platform-port.md）：**这个外设有没有排他性的长时序状态**？有才建 task；没有就是一个库函数 + 内部锁（纯寄存器类器件通常都不需要自己的 task）。

## 7. 门禁与 skill 硬约束

「AI 不可信」「AI 不能改应用层以外」必须落成机器能查的，否则只是文字。

### 7.1 机械门禁（CI）

| 门禁 | 检查方式 | 防的是什么 |
|---|---|---|
| 写入白名单 | `git diff --name-only` 逐个查 `policy.txt` 的写权限（`check_policy.py --write --as <tag>`） | AI 改框架层/平台层 |
| 依赖判定 | `clang -MM` 的真实解析结果逐个查读权限 | 越权 include（`../`、`-I`、`#include_next` 都绕不过真实解析） |
| 符号判定 | `llvm-nm -u` 的未定符号是否出现在该 TU 实际 include 过的头里 | `extern void fw_boot(void);` 这类不 include 就取特权 |
| 解耦检查 | `check_purity.py`：app 不碰 SDK、platform 不碰业务 | 跨层调用 / 平台耦合 |
| 例外白名单 | platform 只调 `fw_event_post` / `fw_event_post_isr` | 反向调用扩大化 |
| 能力目录双向比对 | `api/` 每条能力 ⇔ 某个 service 注册的操作 | 手写文档漂移 → AI 调不存在的接口，**且失败是静默的** |
| 交付格式固定四行 | `Build` / `Host tests` / `Device tests` / `Unverified` | 把编译成功说成硬件验证成功 |
| host 单测 | `cc -std=c11 -Wall -Wextra -Werror` + `tests/*_stubs/` | 框架层是纯逻辑，必须离线可测 |

### 7.2 skill 硬约束

- 只能修改 `policy.txt` 允许的路径（产品仓库里通常是 `apps/demo/<app>/` 与 `apps/app_manifest.c`）；越界立即停止并报告。
- 主任务必须事件驱动、有界等待、有协作退出检查点。
- **禁止** `xSemaphoreCreateBinary` 当锁（无优先级继承）；用 mutex。
- **禁止**忙等 / 关中断超长；长计算必须让出 CPU。
- **禁止**调用设置 task 优先级的接口（框架也没有提供）。
- **禁止** include `platform/`，只能 include `api/`。
- 共享资源必须 obtain/release 成对，且不得假设能改格式。
- **使用任何能力前先查 `cap_available()`**，不得假设本平台一定有。
- 屏幕：不得在应用层请求"全刷"，没有这个接口。
- 每轮完整实现后**必须主动询问是否烧录真机测试**（设备已连接 ≠ 烧录授权）。

## 8. 与 ai-passport 的关系

借鉴其**已被验证的机制**（单一入口 + 路由表、工作流即仓库产物、事实来源优先级链、可执行门禁、固定交付格式、经验飞轮 `docs/reference/`），补上它的四个缺口：

| ai-passport 的缺口 | 本方案 |
|---|---|
| 单板模板，换板 = fork + 改 `bsp_pins.h` | 平台层是外部实现，接口由 `platform/port` 定义 |
| App 模型 = 一 App 一分支，无共存/生命周期 | App = 模块 + task + manifest，0 号管生命周期 |
| skill 只是"给 AI 的工作流"，不是"给 AI 的运行时接口" | 能力目录 + 提交型接口，AI 是**在线操作设备的 agent** |
| 强制 UI 重设计只靠"禁止"，没有"约束"；墨水屏上会炸 | 没有"刷新"接口可用，AI 结构上做不到刷坏屏 |

## 9. 屏幕：单独讨论（本章只记录待决议题）

屏幕是本架构里**唯一**"应用层语义与平台物理特性强耦合"的部分，因此不从通用 port 里过。需要单独定：

1. **切分线在哪**：`disp_commit / 提交合并 / damage 管理 / 刷新策略` 属本仓库；`波形、上电时序、并行传输、面板参数` 属平台包。要精确到什么粒度？
2. **刷新模式词汇表**：`full / partial / fast` 够不够？由谁决定用哪个——应用层、display App、还是平台？
3. **完成后与撕裂**：刷新期间 framebuffer 是否允许修改？双缓冲还是"冻结 + 只改 damage 区"？
4. **IO 与刷新的耦合**：字体在 flash、屏占总线时，"预载到 RAM"的责任在 display App 还是平台？
5. **能力缺失**：某平台没有局刷，`disp_commit` 应降级成全刷，还是返回 `NOT_SUPPORTED`？
