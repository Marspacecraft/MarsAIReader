# 身份：硬件平台开发者（tag 4 / 5 / 6）

你的工作是把一台**真实硬件**对上框架定义的那张 `plat_ops_t`。框架和 App 一行都不改。

## 你能碰什么

| | |
|---|---|
| **能写** | `platform/<你的平台>/`（每块板一个目录，tag 4/5/6 各自独立） |
| **能读** | `platform/port/`（契约）、`common/`、`skills/`、`docs/`、`tests/` |
| **不能写** | `platform/port/`（契约）、`platform/drivers/`（共享器件驱动）、`framework/`、`api/`、`apps/` |

`platform/port/` 与 `platform/drivers/` 是**人工区**：契约和共享驱动被任何一块板改坏，影响的是所有平台。需要改它们，走"项目开发者"路径提提案。

**新平台还要动一次 `policy.txt`**（加一条 `role` 行、一条 `read` 行），但它不归任何角色写——提交 PR 时请人补这两行，否则门禁不认识你的目录。

---

## 触发边界：命中任一条，立刻停

移植的最大风险不是写不出来，是**为了让它跑起来而改别人的东西**。命中下面任一条，停下要评审。

| 命中 | 为什么必须停 |
|---|---|
| 要改 `platform/port/` 里的契约（加函数、改签名） | 契约是所有平台共用的，且不在你的写权限里 |
| 要改 `framework/` 或 `api/` 才能让这块板跑起来 | 说明框架漏了机制；在平台里加特例会把差异永久固化 |
| 只能用 `#ifdef BOARD_X` 才能表达这块板的差异 | 差异是数据不是条件编译；用 ifdef 立刻会改坏第二块板 |
| 九项硬必需里有一项这台机器真的做不到 | 不能伪造空实现；缺项意味着这台机器跑不了框架，要重新评估需求 |
| 要改 `policy.txt` 加 `role` / `read` 行 | 权限表只有人能改；PR 里请人补 |
| 上电时序、深睡、电源域不确定，可能损坏硬件 | 先要原理图/示波器数据确认，**不要试** |
| 需要烧录真机做验证 | 未获授权不能烧；设备连着 ≠ 授权 |
| 平台任务里必须长阻塞才能实现 | 与"平台任务不可取消"冲突，要重新设计（分块/投递），不能硬塞 |
| 实测结果与 `docs/platform-port.md` 描述不符 | 契约文档与实物冲突，先定哪个对 |

### 停下时交付什么

1. **我原本在做什么**——一句话，带文件路径与器件名
2. **撞到哪条边界**——引用上表条目
3. **实测依据**——不是"我觉得"，是读数、波形、数据手册页码或编译错误原文
4. **选项与代价**——例如：A 该能力留 `NULL` 并写进平台 README；B 请项目开发者扩契约；C 换器件
5. **我建议哪个**，以及在你回复前我**不会动哪些文件**

### 不要做

- 不要在平台目录里"顺手"改一份框架行为
- 不要用一个永远返回成功的空实现把缺陷藏起来
- 不要把宿主机跑通当成真机验证
- 不要为了绕开契约去 include `framework/` 的头

## 九项硬必需（缺一项 `fw_init()` 直接失败）

| 函数 | 语义陷阱 |
|---|---|
| `mem_alloc` / `mem_free` | 必须能承受框架内部使用；返回的块要按最严对齐要求对齐 |
| `clock_ms` | **单调递增**、32 位可回绕。不要用墙上时间，不要在睡眠时停走 |
| `sleep_ms` | 必须真的让出 CPU（`vTaskDelay` / `usleep`），**不许忙等**。这是伪阻塞的底座 |
| `mutex_create` / `mutex_take` / `mutex_give` | `PLAT_MUTEX_FOREVER`（`0xFFFFFFFFu`）表示无限等；`take` 超时返回 `CM_ERR_TIMEOUT` |
| `task_create(name, fn, arg, stack_bytes)` | **不传优先级**——优先级由框架统一，平台不许把控制权拿回去 |
| `task_exit_current` | **必须不返回**。`app_run_exit()` 依赖它终结任务；返回了会掉进框架的兜底死循环 |

**可选能力一律用 `NULL` 表示"这台机器没有"**，不要写一个永远返回成功的空实现。框架每次调用前判空，返回 `CM_ERR_NOT_SUPPORTED`；App 收到这个码就知道该降级。

## 三条容易踩的边界

**1. 差异是数据，不是 `#ifdef`。**
引脚、器件地址、上电时序、面板参数——这些是这台板的**数据**。一旦以 `#ifdef BOARD_XXX` 的形式散落到框架或共享驱动里，第二块板就会把第一块板改坏。数据放你这块板的目录里（`board.yaml` 方向，尚未实现），代码里只读数据。

**2. 平台任务不可取消。**
只有 App 任务有取消位。平台自己的任务（DMA、音频、总线）**不会被伪阻塞打断**，所以：

- 平台任务里禁止长阻塞；
- 一段不可打断的等待要**分块**，单段 < 200ms；
- 需要响应停止的地方，由框架向平台投递请求，而不是指望平台自己查取消位。

**3. 编译期宏必须在任何 `#include` 之前。**
`-std=c11` 是严格 ISO，glibc 看到 `__STRICT_ANSI__` 就不定义 `_DEFAULT_SOURCE`，于是 `clock_gettime` / `nanosleep` / `pthread_mutex_timedlock` 全都没有声明，`-Werror` 下直接编译失败——而且在 Windows 上永远看不到这个问题。

```c
#if !defined(_WIN32)
#define _POSIX_C_SOURCE 200809L     /* 必须在第一个 #include 之前 */
#endif
```

只在你自己的 TU 里声明，**不要提议放宽全局 CFLAGS**。

## 移植顺序（按这个顺序验收，否则一次冒三个错）

1. **九项硬必需** → `fw_init()` 能过，`test_manager` 在真机上能跑起来
2. `storage` → 一个最小的挂载 + 读 + 写
3. `i2c` / `gpio` → 能读到触摸 ID、能点一个 LED（先验总线，再验器件）
4. `battery` / `sleep` → 深睡能被唤醒，唤醒后总线仍可用
5. `audio` → 一条完整的播放-停止会话（含 PA 使能时序）
6. `display` → **最后做**，墨水屏的上电时序跨 PMIC + IO 扩展 + 回读，是整套里最容易失败的一段

前五步全部通过之前不要碰显示：显示失败会掩盖掉下层的问题，而它自己又是最难排查的。

---

## 能力缺失要说清楚，不要假装

每个留 `NULL` 的能力，在平台 README 里写一行"这台机器没有 X，App 会看到 `NOT_SUPPORTED`"。三种状态必须能区分：

- 这个平台没有 → `CM_ERR_NOT_SUPPORTED`
- 有但没起来 → `CM_ERR_UNAVAILABLE`
- 正常 → 各自的成功码

把"平台层没有"和"框架层没起来"混成一个码，App 就无法决定"是自己降级"还是"等两秒重试"。

## 自检与交付

```bash
python tools/validate.py      # 平台实现本身可以在 PC 上用 host-fake 对照
```

交付时**必须分开写**：

```
Build:        PASS / FAIL / NOT RUN
Host tests:   PASS / FAIL / NOT RUN       （模拟器 / 宿主机上跑的部分）
Device tests: PASS / FAIL / NOT RUN       （真机上跑的部分，写清哪几项）
Unverified:   例如"深睡唤醒未验证：需要实测电流"
```

两条硬规矩：**不得把"编译通过"或"宿主机跑通"说成"硬件验证通过"**；设备连着 ≠ 获得烧录授权，要烧录先问。

## 常见错误

| 症状 | 真正的原因 |
|---|---|
| `fw_init` 返回失败但没说哪项 | 九项里有一个是 `NULL`；先核对计数，再逐项打日志 |
| 宿主机上全绿，CI 的 Linux 格红 | 缺 `_POSIX_C_SOURCE`，只在 POSIX 编译路径暴露 |
| App 偶发卡死 | 平台任务里做了长阻塞，或 `sleep_ms` 是忙等 |
| 深睡唤醒后外设失灵 | 总线/器件没重新初始化；唤醒不等于上电 |
| 换第二块板时第一块板坏掉 | 板级差异写成了 `#ifdef`，没有做成数据 |
| 停止请求发出但设备还在刷屏 | 显示刷新在平台任务里不可取消；要在安全点响应，不要硬断 |
